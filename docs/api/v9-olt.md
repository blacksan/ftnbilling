# OLT management (V-SOL), server side

The server can read a V-SOL OLT over SSH (or Telnet) and, only when the owner allows it per OLT, configure it and authorise ONUs by itself. The OLT is reached over the router, through a dedicated OLT-management VLAN (default 98) that only the server can reach. When OLT management is off on the server the endpoints answer 404 `not_found`.

**No password is ever returned**: not the OLT login, not the enable password. Saved configurations come back with secrets redacted, to owners only.

| Method and path | Role | What |
|---|---|---|
| `GET /olts/{id}/status` | viewer | `{olt_id, name, configured, protocol, connected, checked_at, error, version, model, sw_version, hw_version, version_note, findings, online, total, onus, auto_found, not_in_inventory, provisioning:{enabled, dialect_checked}, host_key, unparsed}`. `onus` rows: `{pon, id, serial, state, online, rx_power, tx_power, distance, last_down}` (strings as the OLT printed them; empty when not read). `auto_found` rows: `{pon, serial, verdict, detail, first_seen}`; `verdict` is `added`, `ready`, `unknown`, `held` or `failed`. `not_in_inventory` is the `unknown` rows. `version_note` is a warning when the OLT's model or software is not the one the commands were checked against (V1600GS-R, V1.0.5). `findings` are read-only statements about the OLT's own settings (auto-learn on, default SNMP communities, ...) and ONUs on the OLT that are not in the inventory. `unparsed` is raw output the parser could not read (kept so nothing is lost). Read from the last poll (about every 5 minutes) |
| `POST /olts/{id}/test` | operator | Connects, logs in, reads the version. `{ok, version}`. 502 `olt_error` with a plain sentence on failure |
| `POST /olts/{id}/poll` | operator | Reads the OLT now; answers like `status` |
| `GET /olts/{id}/backups` | owner | `{items:[{id, at, why, by, size}]}`, newest first, the last 20 are kept |
| `GET /olts/{id}/backups/{bid}` | owner | `{id, at, why, text, redacted:true}`, `no-store`, audit-logged |
| `PUT /olts/{id}/provisioning` | owner | Body `{enabled?, dialect_checked?, password}`. Needs the owner's password again (403 `invalid_credentials`, 429 `rate_limited` after repeated wrong ones). Provisioning is off by default; it only works when `dialect_checked` is true. Answers like `status` |
| `POST /olts/{id}/plan` | owner | Reads the OLT and answers the exact command list the server would send: `{hash, empty, lines, steps:[{title, lines, independent, unverified}], adds:[{pon, id, serial, label}], notes, warnings}`. Sends nothing. Each step is sent as its own batch: a refused line stops its step and every later step except `independent` ones (the per-ONU lines of ONUs already on the OLT, which need no profile); if an independent step went through after a failure the configuration is saved and the error names the failed, done and skipped steps. `unverified` says which lines of a step the bench grammar does not show (the Pri profile body and its `commit`). A Pri profile that exists but is incomplete is a warning: no ONU is bound to it, new ONUs get the TR-069 WAN per ONU |
| `POST /olts/{id}/apply` | owner | Body `{hash, password}`. The password, provisioning (with `dialect_checked`) and the hash (the plan the OLT has now) are checked in the request; the apply itself (backup, the lines, a save of up to 120 s, re-read and verify) runs in the background: **202** `{started:true, status_url}` with `Location: /api/v1/olts/{id}/job`; poll it for `{backup_id, sent, verified, remaining}`. The job builds the plan again in its own session and compares the hash again, so a plan that changed meanwhile is never sent (the job ends with the error). 409 `bad_state` when provisioning is off, the plan changed since (look again, send the new hash) or a job already runs for the OLT. A command the OLT refuses stops the batch and is audit-logged. If the server stops mid-apply the job status says `interrupted: true, interrupted_kind: "apply"` until the plan is read again (it is built from what the OLT has, so nothing is applied twice) |
| `GET /olts/{id}/job` | owner | The latest background job of the OLT (Secure, Apply or Check now; one at a time per OLT), `no-store`, no secret: `{known, running, done, kind, label, stage, started_at, by, interrupted, interrupted_kind?, interrupted_note?}`; when done also `{finished_at, ok, message}` or `{error}`, plus for `secure` the Secure fields below and for `apply` `{backup_id, sent, verified, remaining}`. `known` is false when no job ran in this server process. `GET /olts/{id}/secure` is the same endpoint (its first name) |

Rules the server keeps for every line it sends: a built-in deny list (erase, factory reset, reboot, format, startup-config delete, `no` on the management interface or VLAN, user or password changes) is checked in the driver and cannot be switched off. ONU auto-provisioning authorises only a GPON serial that is in the inventory (not retired) and assigned to a house served by that OLT and PON; unknown serials are never added (they appear in `not_in_inventory` and the owner is alerted, rate limited), an inventory serial seen on the wrong OLT or PON is held and the owner is alerted. Removing an ONU from the OLT is only ever an explicit owner action.

The TR-069 ACS URL and the shared first-contact ACS login go to the OLT over the CLI, in a Pri profile (`tr069_mng`) that new ONUs are bound to (ONUs already on the OLT get the same per ONU). The login is hidden in every plan, result and audit text.

## Adoption through the router's OLT management port, and "Secure this OLT"

The default way to reach an OLT is a spare router port with the role `oltmgmt` ("OLT management"; the VLAN 98 console snippet stays as a manual fallback, `manual: true`). The server configures the port over the router's REST API with allowed writes only (`/ip/address`, `/ip/firewall/filter`, `/ip/firewall/nat`; never routes, WireGuard, `/user`, `/ip/service` or `/system`):

- the router takes an address in the OLT's factory subnet (default `192.168.8.1/24`, set per router);
- a dst-nat from `wg-ftn`, source `10.99.0.1` only, to `192.168.8.200:22`, on router port `22000 + last octet` (22200);
- a masquerade toward the OLT, and drop rules for everything else to or from the port;
- removing the role removes exactly these rows (comments `ftn: oltm ...`) and nothing else.

When the inventory OLT's MAC is seen on the port the server connects by SSH (host key pinned on first use) and reads `show version`. It adopts the OLT only when the serial equals the inventory serial and the model starts with `V1600`; anything else, and any unknown MAC on the port, is listed under New devices as `possible_olt` (alert rate limited, nothing configured, never attachable to a customer).

Credentials: the stored per-OLT login first. With none, the vendor factory login is tried once (a constant in the server, never shown or logged); a success runs Secure automatically, a failure asks the owner for the login. The owner can always type one.

| Method and path | Role | What |
|---|---|---|
| `GET /olts/{id}/adoption` | viewer | `{stage, next, error, manual, port, steps:[{label, state, detail}], checked_at, mac_seen, ssh_reached, serial_ok, credentials:{stored, source, need_login}, secured, secured_at, can_secure, snmp_off, snmp_note, access_list_note}`. `state` is `ok`, `todo` or `fail`. The same object is `adoption` in `GET /olts/{id}/status`. No password |
| `POST /olts/{id}/adoption/check` | operator | "Check now": the pass over the router's OLT management port for this OLT (it may adopt it and, with the factory login, secure it: minutes). **Changed**: it no longer answers like `adoption`; it starts a background job and answers **202** `{started:true, status_url}` with `Location: /api/v1/olts/{id}/job` (the status endpoint is owner-only; an operator reads `GET /olts/{id}/adoption` afterwards). 409 `bad_state` at once when the OLT has no router, the router has no OLT management port, adoption is off on the server, or a job (or the server's own 5-minute pass) is working on the OLT |
| `POST /olts/{id}/secure` | owner | Body `{password}` (the owner's, step-up). Generates a 24+ character `[A-Za-z0-9]` login and enable password, sets them in `user manager`, logs in again with a new SSH session (and enable) while the old one stays open, and only then runs `write` and stores them sealed. If the check fails the old passwords are put back through the old session and the call fails. Then removes the `public` and `private` SNMP communities (`snmp_note` says SNMP is now off) and limits SSH to the router's OLT-management address: only `login-access-list permit ssh <router> 255.255.255.255` (and `enable` last, only if the list is off). The V1600GS-R keeps a service's rules either all permit (an allowlist: the OLT allows SSH only from listed addresses) or all deny, and refuses the other kind ("add failed, protocol has permit rule,please detele it first!"), so no deny line is sent, IPv4 or IPv6. An OLT whose list already denies SSH by rule is left as it is (note says why). Never telnet, snmp or web rules. A new SSH session must log in before `write`; if it cannot, the permit is removed again (and the list switched off if Secure switched it on), nothing of it is saved and `access_list_note` says "Couldn't restrict SSH; left open". `access_list_done`, `access_list_rules` (read back) and `access_list_finding` (web/HTTPS reachable from the management network; "IPv6 SSH is not restricted" when the OLT has an IPv6 address) report the result. The server can only test from the router's address: check from another PC that SSH is refused. Writes: the passwords' own verified `write`, then one more at the end (the access list's, which also saves the SNMP removal); a `write` that times out reports the last output the OLT showed. `sshd disable` is never sent. Runs in the background: **202** `{started:true, status_url}` with `Location: /api/v1/olts/{id}/job`; the finished job carries `{enable_checked, snmp_removed, snmp_note, access_list_note, access_list_done, access_list_rules, access_list_finding}`. 409 `bad_state` when the OLT is not identified or a job already runs for it |
| `PUT /olts/{id}/credentials` | owner | Body `{user, pass, enable?, password}`: the login the owner typed (step-up). Answers like `adoption`. 409 `bad_state` (nothing stored) while a job or the server's own pass is working on the OLT. It does not check the login; send `adoption/check` for that |
| `POST /olts/{id}/credentials/reveal` | owner | Body `{password}`. `{user, password, enable_password}`, `no-store`, audit-logged (without the password) |

The router port role is `oltmgmt` in `GET/PUT /routers/{id}/ports`. New devices have `class: "possible_olt"` for a device seen on that port that is not a proven OLT of the register.

The deny list keeps blocking `user`, password, `snmp-server` and `login-access-list` commands everywhere except inside the Secure action's own builder, which accepts exact command shapes only.

### Background jobs

Secure, Apply (including the web page's ONU removal) and Check now take minutes, longer than one request may last. Each runs detached from the request on one slot per OLT: at most one job of any kind runs per OLT, and a start while one runs is refused (409 `bad_state`, the message names the running job). The server's own 5-minute adoption pass takes the same slot for each OLT it works on and skips an OLT whose slot is taken, so a pass never logs in to, secures or rewrites the adoption state of an OLT while a job runs on it (and the reverse). The job record lives in the server process; only an Apply leaves a durable mark (`kind, by, at, plan hash`, no secret) from its start to its end, and an interrupted Secure leaves its sealed new login pair. The web page polls `/admin/olts/manage/job-status` (owners) or reloads itself every 5 s (operators) while a job runs.
